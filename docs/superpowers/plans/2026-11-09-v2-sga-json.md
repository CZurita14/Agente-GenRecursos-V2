# V2: sílabos desde el SGA en JSON — plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Copiar el Generador de Recursos al repositorio V2 y reemplazar la entrada por PDF por el SGA: el docente entra con su usuario del SGA, ve las mismas materias que el SGA le muestra y el sistema importa cada sílabo en JSON y genera igual que hoy.

**Architecture:** Una capa `app/sga/` con un `ProveedorSGA` (autenticar, listar materias, obtener sílabo) detrás de una interfaz; hoy solo existe el proveedor simulado, y el real se conecta cuando TI entregue el mecanismo. Al ingresar se sincroniza todo: se autentica, se listan las materias, se importa cada sílabo, se valida (esquema + integridad) y se guarda con el servicio de asignaturas que ya existe. La clave del SGA nunca se guarda. Todo lo que viene después del `SilaboUTI` validado (contexto, menú, razonador, planificador, workers, verificador, revisor, exportación) **no cambia**.

**Tech Stack:** FastAPI, Pydantic 2, PostgreSQL 18, React 18 + TypeScript + Vite, pytest, Docker Compose.

**Spec:** contrato `docs/api-silabo/README.md` + `docs/api-silabo/silabo-api.schema.json`; decisiones del usuario del 2026-11-09 (resumen abajo).

## Decisiones ya tomadas por el usuario

- La autenticación es la del SGA: así el docente tiene en el sistema las mismas materias que en el SGA.
- El mecanismo concreto del SGA lo define TI → interfaz + proveedor simulado; el adaptador real queda pendiente.
- La entrada por PDF se elimina por completo (lector, aislamiento, subida, configuración y pruebas).
- El sistema no aprueba sílabos: consume lo que el SGA entrega y genera. Se muestran todas las materias que devuelve el SGA, sea cual sea su estado.
- La V2 arranca con una copia limpia sobre su commit inicial (`2d09ae0`), sin el historial de V1.

## Global Constraints

- Nunca leer ni imprimir texto de `Silabos/` ni datos personales (secciones I y VII); los mensajes de error nombran la ruta del campo, nunca su valor.
- Nunca imprimir valores de `.env`, claves ni tokens; la clave del SGA no se guarda en ningún lugar (ni base de datos, ni registro, ni memoria después de la llamada).
- `docs/propuestas/` no se copia ni se versiona; nunca `git add -A`.
- El `SilaboUTI` validado debe producir exactamente el mismo contexto que en V1: los 23 prompts de las pasadas, idénticos.
- Push a la V2 solo con aprobación explícita del usuario. Trailer: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Cada tarea actualiza `progress.md` (mismo formato que V1: fecha, tarea, resultado, pruebas, pendientes).
- Rutas relativas a la raíz de la V2; pruebas con `cd backend && python -m pytest`.

## Review Focus

1. **El SGA cae a mitad de la sincronización** (lista bien y falla en el 3.er sílabo): el docente entra igual; las materias que se importaron quedan, y la que falló se marca `no_disponible`, sin borrar la versión anterior → prueba en Tarea 3.
2. **Una materia desaparece del SGA** (cambio de distributivo): el docente pierde el acceso en el siguiente ingreso, pero los recursos ya generados no se borran → prueba en Tarea 3.
3. **El mismo proyecto formativo en dos paralelos** (`…-9999 PARALELO 1` y `PARALELO 2`): se guarda una sola asignatura por `codigo_pf` con un solo sílabo, y el menú se muestra una vez por paralelo → prueba en Tarea 3.
4. **El SGA envía campos extra o datos personales** (correo, cédula, firmas): el traductor los descarta antes de validar y no aparecen en la base de datos, los registros ni los errores → prueba en Tarea 2.
5. **Clave errónea repetida**: bloqueo por usuario tras 5 intentos (como los 5 de hoy con el código por correo) y mensaje genérico que no distingue usuario inexistente de clave errónea → prueba en Tarea 4.
